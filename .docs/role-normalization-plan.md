# Role Normalization Architecture Plan

## Overview

This document outlines the complete plan to normalize the time_entry table by removing redundant `role` and `role_name` columns and using only `role_id` as a foreign key reference.

## Current State

### Database Schema

- `time_entry` table has three role-related columns:
  - `role` (text) - Legacy column, currently stores role ID
  - `role_name` (text) - Redundant, stores role name
  - `role_id` (UUID) - Foreign key to role table (added in migration 008)

### Application State

- Time entries are queried with `SELECT *` which includes all columns
- `role_name` is displayed directly in the UI (TimeEntriesTable lines 142, 170)
- SaveTimerModal uses `role` and `role_name` from draft entries (lines 196-197)

## Implementation Plan

### Step 1: Update Database Query Functions

Update `lib/database.ts` to JOIN with role table:

```typescript
// getUserTimeEntries - Add role JOIN
const { data, error } = await supabaseAdmin
  .from("time_entry")
  .select(`
    *,
    role:role_id (
      id,
      name,
      color_hex
    )
  `)
  .eq("user_id", userId)
  .gt("duration", 0)
  .order("created_at", { ascending: false });

// Transform the response to flatten role data
return data.map(entry => ({
  ...entry,
  role_name: entry.role?.name || null
}));
```

## Rollback Plan

If issues arise:

1. Restore from backup before migration 010
2. Keep role_id column but re-add role and role_name columns
3. Create trigger to sync role_name from role table on INSERT/UPDATE

## Benefits of Normalization

1. **Data Integrity**: Role names always consistent, even if role is renamed
2. **Storage Efficiency**: No duplicate role name storage
3. **Maintainability**: Single source of truth for role information
4. **Flexibility**: Can easily add more role attributes without schema changes
5. **Referential Integrity**: Foreign key prevents orphaned entries

## Notes
